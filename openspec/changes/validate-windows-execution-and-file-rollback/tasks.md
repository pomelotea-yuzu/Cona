- 实测接口条件（只约束原型，不构成产品安全承诺）：
  - AppContainer 进程在环境块缺少 `USERPROFILE`、`APPDATA` 或 `LOCALAPPDATA` 之一时 `CreateProcess` 直接失败（`ERROR_ENVVAR_NOT_FOUND`）；原型把这三项指向容器自有目录，而不继承宿主 profile 路径。
  - 卷根读属性/遍历不可得时，文件型 Node 载荷需要 `--preserve-symlinks-main` 绕行（Node 按路径逐段解析会 stat 卷根）；完成一次性提升权限供给后不再需要，本轮全部用例已以真实形态运行。
  - 祖先链的每一级都需要容器身份的遍历+读属性：实测在 `experiment`、`run-<id>`、`windows-execution-validation`、`output` 任缺一级时，载荷都会在该级 `lstat` 上 `EPERM`。驱动按可达最深处向上自动推导该链，卷根由提升权限供给单独覆盖（驱动不再改写卷根，否则会因缺 WRITE_DAC 而 rc=5）。
  - 容器身份的授权可获得性探测分两个模式：**例行运行只读取 DACL、绝不写入**（防止误删已供给的授权），只报告 `existingContainerAceCount`；写入探测 `--probe-acl-write` 仅用于宿主自有对照目录，用于记录 rc 对照。未提升权限时 `D:\` 卷根、`D:\nodejs` 子项样例、`C:\Program Files\Git` 的写入探测均返回 rc=5（该证据来自提升前的单次探测）；完成提升权限供给后这四个运行时目标上 `existingContainerAceCount` 均为 1，且经一整轮用例运行后仍保持。注意 rc 描述“宿主本次能否改写该 DACL”，不等同于“容器是否已获得访问”。
  - 运行时供给成本实测（供路线取舍）：node.exe 88.5 MB；pnpm 的 corepack 树仅 54 文件／0.6 MB；Git 安装树 7421 文件／414.9 MB。本机 `C:\Program Files\Git\bin\git.exe`、`cmd\git.exe`、`mingw64\bin\git.exe` 均存在，可作为 E03 的 Git 入口。
  - AppContainer 会把 `LOCALAPPDATA` 与 `TEMP` 重定向到容器自有 package 目录，显式环境列表对此不完全权威；结论按实际值记录。
  - **AppContainer 与 Git for Windows 不兼容（E03 受阻的直接原因）**：`git --version` 可用，但任何需要解析工作目录的命令（`init`、`config`、`status`）都返回 128 `fatal: unable to get current working directory: Permission denied`；显式 `--git-dir/--work-tree`、`init --bare` 加绝对路径均无效。同一进程树内 Node 的 `process.cwd()` 与 `fs.realpathSync('.')` 正常，因此这不是 AppContainer 的普遍限制，而是 Git 自身的目录解析在该隔离下被拒。已尝试的绕行都失败，未放宽隔离冒充通过。
  - **容器内以匿名管道（stdio `pipe`）接管控制台子进程会挂起**：实测 `spawnSync(git, ['--version'])` 走管道时不返回，改用文件句柄重定向（`stdio: ['ignore', fdOut, fdErr]`）约 50ms 正常返回；该对照已固定进 E03 载荷（`control-stdio-pipe-capture` 在可终止子进程中执行，超时即杀）。后续正式执行器捕获工具输出必须用文件句柄而非匿名管道。
  - 容器身份在仓库目录上的授权由驱动在结束时回收并清扫历史遗留；本轮结束后 `D:\Cona` 与 `output` 上容器 SID 计数为 0。
