# Review：validate-windows-execution-and-file-rollback

评审日期：2026-10-18
评审对象：[proposal.md](proposal.md)、[design.md](design.md)、[tasks.md](tasks.md)、[validation-matrix.md](validation-matrix.md)、[windows-execution-prototype/spec.md](specs/windows-execution-prototype/spec.md)、[workspace-recovery-prototype/spec.md](specs/workspace-recovery-prototype/spec.md)，并对照 [统一设计方案](../../../docs/drafts/2026-10-18-Agent独立产品统一设计方案.md) 第 5.3、5.4、9.2、11.4、12、13.3、16、17 节与 [openspec/config.yaml](../../config.yaml) 的产物规则。
评审性质：提案阶段的文档一致性与完备性评审，不含原型代码审查（尚无实现）。

## 1. 总体评价

本 change 是一份质量较高的验证型提案。它准确地把"已确认产品决策、设计默认、未验证假设"分层处理，未把 AppContainer／ACL／Job Object 候选机制写成已交付的安全能力，且在 proposal、design、tasks、matrix 四处一致地声明"提案齐备不等于验证完成"。安全论证采用了正确的默认立场：

- 隔离初始化失败即拒绝执行，明确无"完整用户权限降级"分支（与 config.yaml 的硬规则一致）；
- 版本与回退以内容校验和冲突保留为原则，拒绝"只存哈希或工具事件即视为可恢复"、拒绝可写硬链接共享、拒绝多文件操作的全目录原子性假设；
- 验证结论区分通过／失败／受阻／未测，并要求正常工作正例与越界反例同时成立，防止"全拒绝即安全"的伪通过；
- 测量不预设未经批准的数值阈值，不把单机结果扩大为全部 Windows 兼容。

结论：**提案可进入实施阶段**，以下问题均为改进项，不构成阻塞。

## 3. 发现的问题

### 3.1 中等（建议在实施前补充）

**M1. 缺少"采用／调整／暂缓"的判定口径。**
tasks 7.4 与 design §8 把路线裁定作为最终出口，但 design 又明确"当前无已批准的数值阈值"。两者之间缺一层决策规则：兼容性失败到什么程度算"调整"而非"暂缓"、资源开销由谁裁定可接受。建议在 validation-matrix 的结论模板中显式写明：数值裁定由用户基于脱敏报告做出，报告只提供测量事实与建议，且哪些用例失败必然导致暂缓（如 E12、E04 类安全负例失败）。目前结论模板第 5、6 条有此方向的表述，但未指出安全负例失败时不可用"整体利大于弊"覆盖。

**M2. P01（安装与权限）缺少对应规范场景。**
windows-execution-prototype 的"验证结论可复现且区分门槛"要求记录环境、工具版本与有效策略，其"资源开销测量"场景覆盖 P02／P03，但"首次设置权限、额外服务要求、安装权限"（P01、task 1.1／7.1）没有对应的 Scenario。若安装需要管理员权限或额外服务，这直接影响"轻量易用"判断，应在规范中留有可核查行为（例如：环境报告必须列出所需提升权限与额外服务，缺失时记受阻）。

**M3. 并发多任务场景未显式界定。**
两份 spec 多处要求保护"其他任务"资源（E04、E07 覆盖跨任务访问拒绝），但矩阵没有验证两个 run 并发时版本存储、交付账本、停止核查的相互影响。原型按单机单任务验证可以接受，但应二选一：在 design 的 Non-Goals 中显式声明"不验证并发多任务下的账本与版本存储一致性"，或在矩阵补一条并发用例。当前处于两者之间的含糊状态。

### 3.2 轻微（可择机修正）

**m1. "启动前授权"没有专属用例。**
proposal "What Changes" 首条列出"启动前授权"，但矩阵中 E12 是通过故障注入覆盖授权检查失败，E07 覆盖宿主接口层的跨任务／任意路径拒绝；"无授权或授权范围外的执行请求在正常路径下于启动前被拒绝"未显式成行。建议并入 E12 或新增一行，避免验证时漏测正常路径的拒绝。

**m2. 停止后"持续观察"窗口未定义。**
E11 与 spec"后台与脱离尝试"要求停止后持续观察期间无继续写入，但未给出观察时长或判定口径，不同 run 的证据可比性会受影响。建议给出可配置的固定观察窗口并在结果中记录实际值。

**m3. E／F／P 前缀含义未定义。**
矩阵直接使用 E01、F01、P01 编号，未说明前缀语义（推测为 Execution／File／Performance）。一行说明即可。

**m4. tasks.md 小节标题为中文。**
config.yaml 要求 "Keep OpenSpec structural headings … in English"。`## 1. 实验环境与可复现样例` 等小节标题是否属于"structural headings"存在解释空间；若严格执行，应改为英文标题。两份 spec 的 Requirement 名称为中文属内容范畴，不在此列。

**m5. 路径措辞不一致。**
proposal Impact 以陈述式写"运行证据放在 `output/windows-execution-validation/<run-id>/`"，design §8 写"运行输出建议放在"。同一约定一处陈述一处建议，建议统一为"约定"或均为"建议"。

**m6. Impact 混合已完成动作与新增产物。**
"当前新增 OpenSpec 配置、提案…，并更新现有两份设计文档的状态和仓库信息"把已做的文档更新与本 change 新增内容写在一句内，归档时不易区分哪些属于 change 交付物、哪些是同步维护。建议拆句表述。

## 4. 与产品门槛的对齐确认

- §12.3 门槛表六项中，本 change 覆盖"正常工作（Node／pnpm／Git 部分）"、"文件与凭据"、"网络与宿主接口"、"子进程与停止"、"初始化与异常"、"交付与轻量"，唯"至少一条选定文档转换路径可用"按既定决策留给单独 change，且三处（proposal Impact、design §8 末、matrix 末）都重申不解除该门槛——处理正确。
- §12.2"直接修改原项目作为明确选择的工作方式"未纳入本 change 验证范围。鉴于交付路径已覆盖原项目写入与回退（F05／F06），此取舍合理，但建议在 design Non-Goals 补一句"不验证绕过副本直接修改原项目的模式"，消除歧义。
- config.yaml"Never silently fall back to unrestricted execution when isolation fails"由 spec"执行在隔离完成后才能开始"及 E12 直接落实，闭环成立。

## 5. 结论

提案结构完整、内部一致、与既有设计门槛对齐良好，安全立场保守且可证伪，任务与验证矩阵互相闭合。建议按 3.1 的三项（M1 判定口径、M2 P01 规范场景、M3 并发范围声明）补充后进入 task 1.1 的环境检查；3.2 各项可与实施同步修正。上述问题均不需要重写提案主体。
